# MCP insights

- [2026-10-04] **Codebase Patterns**: The run-events SSE route has no "done" frame; the server just closes the response when the run completes, so end-of-stream IS the completion signal and frame payloads must not be parsed for status. After the stream ends, read the outcome with `GET /pulls/:id/reviews` (then `/runs` for status + error). The route is exempt from rate limiting, so waiting costs one request instead of a polling loop. Evidence: `server/src/modules/reviews/adapters/inbound/http/routes.ts:52-56,73`, `mcp/src/adapters/outbound/http/wait-for-run.ts:20-21,106`.
- [2026-10-04] **Recurring Errors & Fixes**: A 429 from the `@fastify/rate-limit` plugin and a 429 from the LLM provider reach the client as the same envelope (`code: "rate_limited"`, provider-flavoured message), because the global error handler maps any error with status 429 to it. The MCP server cannot tell them apart, so it maps every 429 to one hint ("Review rate limit reached (10/min)..."), which can be wrong when the provider is the limiter. Evidence: `server/src/app.ts:102,173-176` (handler + plugin registration), `server/src/modules/reviews/adapters/inbound/http/routes.ts:35` (10/min on `POST /pulls/:id/review`), `mcp/src/application/errors.ts:51-52`. Derived from reading the code; not exercised against a live API.
- [2026-10-04] **Decisions**: The server uses the low-level `Server` with hand-written JSON Schema instead of `McpServer.registerTool`, so `tools/list` stays inside the 800-token budget (no generated `title`/`outputSchema`/Zod-derived noise); Zod is used only to validate call arguments. The `tools/call` handler is annotated `Promise<CallToolResult>` explicitly. Reason for the annotation per the implementation notes: without it the SDK 1.32 `setRequestHandler` result typing rejects the handler's return type (index-signature mismatch); not re-verified here, so if you simplify it, run `npm run typecheck`. Evidence: `mcp/src/adapters/inbound/mcp/server.ts:3,28-32`, `mcp/test/tools-list.test.ts:178-182` (budget test).
- [2026-10-04] **Codebase Patterns**: `POST /pulls/:id/review` is fire-and-forget: it creates the `agent_run` rows, starts execution in the background and returns `{runs:[{run_id,...}], reviews: []}` immediately. A blocking tool must therefore wait on the SSE stream and then fetch the review itself; the HTTP response never contains findings. Evidence: `server/src/modules/reviews/service.ts:144-150`, `mcp/src/application/use-cases/run-agent-on-pr.ts` (start -> `waitForRun` -> `listReviews`).
- [2026-10-04] **Codebase Patterns**: A `run_id` cannot be resolved back to a PR over the current API (run routes are `/runs/:id/events`, `/runs/:id/trace`, cancel, delete; run listings are keyed by pull: `/pulls/:id/runs`, `/pulls/:id/runs/active`). Hence `get_findings` is keyed by `repo` + `pr` (+ optional agent), not by `run_id`; supporting lookup by run needs a new server route. Evidence: `server/src/modules/reviews/adapters/inbound/http/routes.ts:55,102,108,121,128`.
- [2026-10-04] **Codebase Patterns**: `get_blast_radius` passes the route response through unchanged except for caps and `clipText`; `degraded` and its reason are returned as data with a fixed hint, never thrown. Evidence: `mcp/src/domain/blast-shape.ts`, `mcp/src/application/use-cases/get-blast-radius.ts`.
- [2026-10-04] **Recurring Errors & Fixes**: `node_modules` in this repo were installed on macOS, so vitest and tsx fail in a Linux sandbox (missing rollup/esbuild linux binaries); only `tsc` and `depcruise` run there. Run the test suites on the host. Evidence: `ls client/node_modules/.pnpm | grep rollup`.
