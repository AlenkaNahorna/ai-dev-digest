1. **server/src/modules/tags/application/use-cases/assign-tag.ts**: The use-case imports `Container` (the composition-root/DI wiring type from `platform/container.js`) and reaches into it as `container.tags.repository`, so the application layer depends directly on infrastructure wiring instead of declaring its own port dependency; this inverts the intended dependency direction and makes the use-case untestable without the full container shape.

2. **server/src/modules/tags/adapters/inbound/http/tags.routes.ts**: The HTTP adapter imports and calls `createAssignTag` directly from `application/use-cases/assign-tag.ts` and passes it the whole `Container`, coupling the inbound adapter to the use-case's "pull a repository out of a container" construction style rather than being handed an already-assembled use-case/port at the composition root; adapters should depend only on application-layer contracts, not participate in wiring concrete dependencies out of a global container.

3. **server/src/modules/tags/adapters/outbound/persistence/tag-repository.ts**: `createTagRepository()` imports `db` directly from `../../../../../db/client.js` (a module-level singleton) instead of receiving a database handle via constructor injection, hardcoding a global infrastructure dependency into the adapter and preventing isolation/swapping for tests.

4. **server/src/modules/tags/adapters/outbound/persistence/tag-repository.ts**: The file defines a `TagResponseDto` (snake_case `pull_id` field) inside the persistence adapter and returns it from `assign()`, but the `TagRepositoryPort` contract (`application/ports/tag-ports.ts`) declares `assign()` as returning `Promise<TagRow>` (camelCase `pullId`); the adapter's actual return value does not satisfy its own port contract, and an outbound persistence adapter should not be shaping an HTTP-facing response DTO (snake_case) at all — that is a presentation-layer concern leaking into persistence.

5. **server/src/modules/tags/adapters/inbound/http/tags.routes.ts**: The route handler casts `request.params` and `request.body` with untyped `as` assertions instead of validating input against a schema, so arbitrary/malformed input can flow uncast into the application layer — a leaky boundary where the inbound adapter fails to enforce the contract it is supposed to guard.

6. **server/src/modules/tags/index.ts**: The barrel file re-exports symbols from every layer (`application/ports`, `application/use-cases`, `adapters/outbound/persistence`, and `adapters/inbound/http`) together via `export *`, collapsing the onion's layer boundaries into one flat public surface; this lets any external consumer import adapter/persistence internals (e.g. `createTagRepository`) through the same path as application ports, erasing the layering the folder structure is meant to enforce.

7. **server/src/modules/tags/application/use-cases/assign-tag.ts**: The use-case has no handling for repository/persistence errors surfaced from `adapters/outbound/persistence/tag-repository.ts` (e.g. the `statusCode`-annotated `Error` thrown on failed insert); this infrastructure-specific error shape implicitly crosses from the outbound adapter through the application layer up to the inbound adapter without translation at any boundary — a leaky abstraction where persistence-layer error semantics are implicitly part of the use-case's behavior.
