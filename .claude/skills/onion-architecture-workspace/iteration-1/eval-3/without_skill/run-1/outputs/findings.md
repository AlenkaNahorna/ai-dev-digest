1. **server/src/modules/notes/domain/note-policy.ts**: The domain layer imports and calls `simple-git` (an external process/IO-bound library) and exports an async `lastEditorEmail` function that shells out to git, which means pure domain logic is coupled to infrastructure/IO — the innermost layer must have zero outward dependencies, and a domain file should not perform filesystem/process operations at all.

2. **server/src/modules/notes/application/use-cases/summarize-note.ts**: The use case directly imports the `openai` SDK and instantiates an `OpenAI` client at module scope, bypassing the application's own port/adapter abstraction (`NoteRepositoryPort` exists for the repository, but no port exists for the LLM) — this hardwires the application layer to a concrete third-party vendor and makes the use case untestable without hitting the real OpenAI client.

3. **server/src/modules/notes/application/use-cases/translate-note.ts**: Same violation as summarize-note.ts — direct `openai` import and client instantiation inside the use case, with no `SummarizerPort`/`TranslatorPort` abstraction, so the application layer depends on a concrete outward adapter instead of an inverted port.

4. **server/src/modules/notes/application/use-cases/summarize-note.ts** and **server/src/modules/notes/application/use-cases/translate-note.ts**: Both files duplicate the identical OpenAI client construction (`new OpenAI({ apiKey: process.env.OPENAI_API_KEY })`) and nearly identical chat-completion call logic — this cross-cutting LLM-access logic should be factored into a single shared adapter/port rather than copy-pasted into two use cases.

5. **server/src/modules/notes/adapters/inbound/http/notes.routes.ts**: The HTTP (inbound) adapter imports `slugifyNoteTitle` from `server/src/adapters/note-slugify.ts` and calls it directly inside the route handler to compute `slug`, placing presentation/formatting business logic (slug derivation) in the transport layer instead of the application or domain layer.

6. **server/src/adapters/note-slugify.ts**: This slugify utility is a pure, note-domain-specific business rule (how a note title becomes a slug) but lives in the generic cross-cutting `adapters/` location outside the `notes` module entirely, instead of being colocated as a module-local domain/application concern — it's a misplaced shared utility that couples an unrelated top-level folder to note-specific semantics and reaches across module boundaries (`notes.routes.ts` imports it via a deep relative path `../../../../../adapters/`).

7. **server/src/modules/notes/adapters/inbound/http/notes.routes.ts**: The route handler reaches past the use-case/application layer to invoke `slugifyNoteTitle(lang)` directly on the query parameter and merges its result into the response alongside the use case's output, meaning the HTTP adapter is performing data transformation/business logic rather than purely delegating to the application layer and shaping transport I/O.

8. **server/src/modules/notes/application/use-cases/summarize-note.ts**: `isValidNoteTitle` from the domain layer is invoked only to decide whether to silently return `undefined` (treated the same as "not found"), conflating a domain validation failure with a repository "not found" case and swallowing the distinction without surfacing it as a meaningful application-level error/result — this blurs the use case's responsibility to translate domain outcomes into explicit application semantics.
