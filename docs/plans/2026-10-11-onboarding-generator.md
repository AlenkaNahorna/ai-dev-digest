## Objective

Implement a repository-specific persisted five-part onboarding tour, generated from an indexed revision using the existing LLM provider infrastructure. Successful indexing schedules generation automatically; manual regeneration retains the previous successful result. Explicit sharing publishes the exact displayed version as a durable, revocable public snapshot with no private API access on the public screen.

## Recommendations

- Add a dedicated `contracts/onboarding-generator.ts` and feature module instead of repurposing loosely typed legacy `Onboarding` contracts. The existing `onboarding` table is only `repo_id/json/generated_at`; preserve it and use new named feature tables. This avoids treating unknown legacy JSON as validated source provenance.
- Use a typed, bounded architecture node/edge representation and render an SVG diagram with escaped labels. The trade-off is a deliberately simple diagram; it avoids accepting executable Mermaid syntax, HTML, callbacks, or links from model output. A textual summary remains available, and missing graph evidence has an explicit fallback.
- Reuse `Container.llm` and existing configured model/provider selection, not the review pipeline itself. Reviews ground findings against PR diffs; onboarding grounds paths, source IDs, and graph relationships against its own captured evidence.
- No extra approval prompt is needed for each Share click. Label the action as public publication of the currently displayed version, show that version's content/provenance, and provide owner-only Revoke controls.

2. **[server] Capture bounded, revision-consistent evidence** — AC-2–AC-4, AC-12–AC-18, AC-21–AC-23.
   - Files/areas: `server/src/modules/onboarding-generator/{domain,application/ports,adapters/outbound/providers}/`; narrow changes to `server/src/modules/repo-intel/service.ts` and its outbound persistence; feature-owned Git evidence adapter using installed simple-git, or a narrow reusable revision-read adapter if genuinely reused.
   - Capture source SHA, index timestamp, indexer version, status and evidence from one completed index. `getRepoMap`, top-ranked paths, critical paths and symbols are candidates, not proof that every partial index has graph data. Require a valid SHA and actual usable evidence; empty partial/degraded states remain unavailable.
   - Current repo-intel storage is mutable and full indexing deletes/replaces rows in several calls. Serialize all full/incremental/resync writes and onboarding evidence capture per repository with the same database-backed lock (released in `finally`, on a dedicated connection/session). Read index state and materialized facts while holding that lock; verify the captured identity before releasing it. Do not rely on a process-local mutex, file count, or before/after timestamp alone. Pin all Git tree/blob reads to the captured SHA so a subsequent clone reset cannot change docs/excerpts.
   - If extending Git capability, keep provider details out of application code. Existing `GitClient.readFile` reads the live worktree and is insufficient for revision reads. Validate a full commit hash, relative paths, reject NUL/traversal/absolute paths and symlink entries, use Git argument arrays without shell execution, and check blob size before buffering. Missing/unreachable revisions produce a safe failure; never substitute current HEAD.
   - Discover relevant README/CONTRIBUTING, docs/specs, package manifests and local setup configuration directly from that Git tree, independently of Project Context. Exclude dependency/build/git/vendor output, env credentials, keys/certificates, binary/invalid text and secret-bearing documents. Record source IDs and readable path inventory for output grounding. Only environment variable names/placeholders may survive evidence screening.
   - Engineering defaults: at most 20 documents, 32 KiB per document, 128 KiB combined document text; 20 ranked files, 10 critical chains of at most 8 paths, 100 symbols, 30 source excerpts of at most 4 KiB; maximum 24,000 evidence tokens and 256 KiB serialized evidence. Check byte/token limits before concatenation and report sampled/skipped/truncated evidence. Cap tree enumeration and reject an oversized inventory with a safe bounded fallback.
   - Skills implementer should apply: `onion-architecture` — ports own Git/index access, provider adapters own concrete queries; `drizzle-orm-patterns` — transactional consistent reads/locks; `postgresql-table-design` — serialize shared update/read access explicitly; `security` — traversal, injection, resource bounds and secret exclusion; `zod` — bounded path/source validation; `typescript-expert` — unknown inputs narrowed; `engineering-insights` — index completeness and UTF-8 caveats.

3. **[server] Generate and durably schedule tours** — AC-2, AC-5–AC-10, AC-22, AC-32.
   - Files/areas: `server/src/modules/onboarding-generator/application/{ports,use-cases}/`, its outbound LLM/persistence/jobs adapters and module factory; `server/src/platform/container.ts`; `server/src/modules/repo-intel/service.ts`; feature prompt in `server/src/prompts/`.
   - Inject narrow evidence, repository, scheduler, clock and LLM ports. Resolve the existing provider/model at composition time; missing settings/keys become a safe configuration failure. Do not hardcode a second credential mechanism or alter reviewer-core's PR grounding behavior.
   - Assemble trusted instructions plus escaped/delimited untrusted evidence, with no model tools, execution or host-file access. Request schema-constrained structured output through the installed provider abstraction. Validate every output reference against captured paths/source IDs; validate diagram endpoints/relationships against available graph evidence. Unsupported claims must become explicit unavailable sections, not invented paths or commands. Every setup row cites a provided doc/config source; first tasks remain suggestions with checkable outcomes.
   - Bound response to 64 KiB, section text to 8 KiB, diagram to 20 nodes/30 edges, critical/reading entries to 20 each, commands to 20, tasks to 5, task files to 10. Permit at most one format-repair attempt, using the same captured evidence and request identity; never relax schema/grounding. Screen output for secret patterns and unsafe links before storing or sharing. Provider call deadline 60 seconds; total request lease 120 seconds.
   - On usable completion of `indexRepo`, `refreshIndex`, and `resyncRepo`, persist an automatic generation request and enqueue its own job; preserve each indexing method's `IndexResult`. Do not wait on the generation job's `done` promise. Cover incremental fallback-to-full and no-op refresh, and do not schedule duplicates for unchanged source SHA/index timestamp/indexer version. Never allow generation failure to turn a successful index into failed indexing.
   - The existing JobRunner uses Promise.race timeouts and does not restore queued work on restart. Add feature-scoped durable request reconciliation at boot (not during GET): resume queued requests and reclaim expired leases. Use attempt fencing so timed-out/previous-process completions cannot publish. Transition a request to running, clear/replace active attempt on retry, and condition success/failure writes on request and attempt identity. A newer manual/automatic request supersedes the old pointer; old workers cannot replace content or error state.
   - Return pending acceptance only after durable request creation; enqueue failures remain explicitly recoverable by reconciliation or retry. Keep safe error categories such as configuration, evidence_unavailable, invalid_output, timeout and provider_failure; never persist raw provider stacks/prompts as public-readable errors.
   - Skills implementer should apply: `onion-architecture` — narrow injected ports and composition-root wiring; `fastify-best-practices` — encapsulated registration and explicit error handling; `drizzle-orm-patterns` — atomic claims/CAS publication; `zod` — validate model JSON rather than trusting JSON.parse; `security` — bounded AI generation, untrusted-data isolation and safe logs; `typescript-expert` — exhaustive lifecycle/error unions; `engineering-insights` — preserve successful persisted data during retries.

## Risks / open questions

- Existing indexing does not provide immutable historical graph snapshots. The shared database-backed index/capture lock and materialized evidence are required, not optional; a second index must not alter graph rows during evidence capture. This is the main integration risk.
- Existing job timeouts do not cancel a running promise. Feature request/attempt fencing must protect persistence even when the provider ignores timeout; recovery cannot rely on the generic JobRunner's memory queue.
- Legacy `created_by = null` has no proven owner; fail closed for owner mutations and document the condition, rather than guessing system-user ownership.
- Secret screening cannot prove arbitrary prose contains no sensitive business information. Share explicitly publishes the reviewed tour; raw docs/prompts/credentials are excluded, and creation uses the exact displayed version.
- Public internet accessibility requires a reachable configured `webOrigin` and a real production AuthProvider. Deployment, tunnels and production-auth setup remain outside scope; local public routes still function anonymously.
- Docker/browser infrastructure may be unavailable in the execution environment. Preserve the tests and report precisely which checks could not run; do not infer success.
- No unresolved user choice changes the feature's architecture. Engineering defaults above can be adjusted only with recorded validation evidence and without weakening AC coverage.
