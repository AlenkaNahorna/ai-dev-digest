## Objective

Implement a repository-specific persisted five-part onboarding tour, generated from an indexed revision using the existing LLM provider infrastructure. Successful indexing schedules generation automatically; manual regeneration retains the previous successful result. Explicit sharing publishes the exact displayed version as a durable, revocable public snapshot with no private API access on the public screen.

## Recommendations

- Add a dedicated `contracts/onboarding-generator.ts` and feature module instead of repurposing loosely typed legacy `Onboarding` contracts. The existing `onboarding` table is only `repo_id/json/generated_at`; preserve it and use new named feature tables. This avoids treating unknown legacy JSON as validated source provenance.
- Use a typed, bounded architecture node/edge representation and render an SVG diagram with escaped labels. The trade-off is a deliberately simple diagram; it avoids accepting executable Mermaid syntax, HTML, callbacks, or links from model output. A textual summary remains available, and missing graph evidence has an explicit fallback.
- Reuse `Container.llm` and existing configured model/provider selection, not the review pipeline itself. Reviews ground findings against PR diffs; onboarding grounds paths, source IDs, and graph relationships against its own captured evidence.
- No extra approval prompt is needed for each Share click. Label the action as public publication of the currently displayed version, show that version's content/provenance, and provide owner-only Revoke controls.

## Steps

0. **[server] Prototype the per-repository index/capture lock (de-risking spike)** — prerequisite for AC-4, AC-10, AC-21.
   - The repository has no advisory-lock precedent (`grep advisory` finds only a comment in `knowledge.ts`); `db.transaction` is used elsewhere but never a session lock. The plan's main integration risk therefore rests on an unproven mechanism, so verify it before building on it.
   - Prototype a small feature-agnostic lock port (for example `RepoIndexLock.withLock(repoId, fn)`) backed by `pg_advisory_lock` on a **dedicated connection**, released in `finally`. Prove with a throwaway integration test that: two overlapping full/incremental indexings of one repo serialize; different repos do not block each other; the lock is released when the holder throws; the lock is released when the connection/process dies (session-level locks vanish with the connection); a capture that waits too long fails with a bounded timeout rather than hanging.
   - Decide here, and record in the plan's risk section, whether the existing pool can supply a dedicated connection or a separate small client is needed. If advisory locks prove unworkable (for example behind a transaction-pooling proxy), fall back to a lease row with fencing token, and update Steps 2–3 before continuing.
   - Done when: the spike test passes on a disposable PostgreSQL, the chosen mechanism and its failure modes are written into the plan, and Steps 2 and 3b reference it. Keep the lock port; discard only the throwaway test scaffolding.
   - **Outcome (2026-10-11, executed):** advisory locks work. `PgAdvisoryRepoIndexLock` (`server/src/platform/repo-index-lock.ts`) reserves a dedicated connection from the existing postgres-js pool (`db.$client.reserve()`, no second client needed), polls `pg_try_advisory_lock(hashtextextended('devdigest:repo-index:<repoId>', 0))` so the wait is bounded (`LockTimeoutError`), and releases in `finally` (plus a defensive `pg_advisory_unlock_all()` so a pooled connection can never keep a lock). `server/test/repo-index-lock.it.test.ts` passes on PostgreSQL 16: same-repo overlap serializes, different repos do not block, the lock is released when the holder throws and when its backend is terminated, and a busy lock fails with a bounded timeout. Failure modes: not valid behind a transaction-pooling proxy (PgBouncer transaction mode); the documented fallback is a lease row with a fencing token behind the same `RepoIndexLock` interface. Indexer entry points (`indexRepo`, `refreshIndex`, `resyncRepo`) take the lock; `runIncremental → runFullIndex` is an internal call inside one hold, so there is no re-entrant acquisition.

Require a valid SHA and actual usable evidence; empty partial/degraded states remain unavailable.

Serialize all full/incremental/resync writes and onboarding evidence capture per repository with the same database-backed lock (released in `finally`, on a dedicated connection/session). Read index state and materialized facts while holding that lock; verify the captured identity before releasing it. Do not rely on a process-local mutex, file count, or before/after timestamp alone. Pin all Git tree/blob reads to the captured SHA so a subsequent clone reset cannot change docs/excerpts.

Validate a full commit hash, relative paths, reject NUL/traversal/absolute paths and symlink entries, use Git argument arrays without shell execution, and check blob size before buffering. Missing/unreachable revisions produce a safe failure; never substitute current HEAD.

## Risks / open questions

- Existing indexing does not provide immutable historical graph snapshots. The shared database-backed index/capture lock and materialized evidence are required, not optional; a second index must not alter graph rows during evidence capture. This is the main integration risk.
- Existing job timeouts do not cancel a running promise. Feature request/attempt fencing must protect persistence even when the provider ignores timeout; recovery cannot rely on the generic JobRunner's memory queue.
- Legacy `created_by = null` has no proven owner; fail closed for owner mutations and document the condition, rather than guessing system-user ownership.
- Secret screening cannot prove arbitrary prose contains no sensitive business information. Share explicitly publishes the reviewed tour; raw docs/prompts/credentials are excluded, and creation uses the exact displayed version.
- Public internet accessibility requires a reachable `PUBLIC_WEB_ORIGIN` (the current `webOrigin` is hard-wired to `http://localhost:<WEB_PORT>` and cannot produce external links) and a real production AuthProvider. Deployment, tunnels and production-auth setup remain outside scope; local public routes still function anonymously.
- Docker/browser infrastructure may be unavailable in the execution environment. Preserve the tests and report precisely which checks could not run; do not infer success.
- Advisory locks have no precedent here and may not survive a transaction-pooling proxy; Step 0 settles this before dependent work, with a lease-row-plus-fencing fallback.
- LLM cost: every successful index can trigger a generation. The per-repository daily budget, the disable switch and recorded per-request cost bound it, but default numbers are guesses to be tuned from the first measured costs.
- Storage growth: immutable versions and snapshots accumulate; the retention rule bounds private versions only. Snapshots persist until revoked and have no expiry by design (spec proposal deferred).
- Ownership model: "owner = `repos.created_by`" is an assumption. Repositories created by one person and maintained by another will not let the maintainer share until a co-owner concept exists.
- Existing indexed repositories get no automatic tour until their next index or an owner's explicit Generate action; this is intentional to avoid a cost spike.
- No unresolved user choice changes the feature's architecture. Engineering defaults above can be adjusted only with recorded validation evidence and without weakening AC coverage.
